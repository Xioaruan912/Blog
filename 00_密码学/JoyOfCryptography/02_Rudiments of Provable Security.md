# 2.1.Attack scenarios as libraries

OTP开始的时候 我们设立了一个 攻击场景 然后构建出了一个 子程序 敌手调用子程序攻击OTP

这里我们开始聚焦如何更好定义出一个攻击场景和子程序（因为我们后面可能会遇到多个子程序问题）

- 一些攻击场景中，受害者可能有多个行为
- 一些攻击场景中，敌手可能强迫受害者操作一些内容

## 库

为了使用多个子程序，而不是单独子程序，我们定义出**攻击场景作为库**

> 库

库是子程序的集合，我们将库以具体的伪代码形式指定出来，并且包含下面特点

1. 所有变量都是库中私有的，调用程序调用库无法取得变量
2. 所有变量都是库中共有的，库中的所有子程序都可以调用到库中变量
3. 定义在子程序之外的代码，都会最先执行，一般是初始化全局变量
4. 一些确定的变量或者类型会初始化为默认值

| 变量名字 | 初始值 |
| -------- | ------ |
| 布尔变量 | False  |
| 整数类型 | 0      |
| 集合类型 | 空集合 |
| 数组类型 | 空数组 |

这里就是一些基本的库的定义，下面我们会使用一个例子说明

> 下面是一个带有全局变量D和两个子程序的库

```
D <- {1,2,3,4,5,6} //这里是一个全局变量 下面所有的子程序都可以访问
Guess(G)：
	return D==G //这里是库中的一个子程序
REROLL():
	D <- {1,2,3,4,5,6} //这里是库中的另一个子程序
```

之前我们知道 我们要求敌手 控制子程序攻击 并且得到输出内容

那么在这里 敌手A 就是叫做 调用程序 **calling program**

# 2.2. Interchangeable libraries

这里我们需要说明一个新的库类型，可互相交换库

我们依旧使用OTP的例子来说明，安全性我们说过，敌手通过子程序攻击的情况下，得到的密文C是均匀分布的随机值，那么其实还存在一个子程序描述这个情况：

![image-20261020145343425](https://raw.githubusercontent.com/Xioaruan912/pic/main/20261020145343461.png)

现在我们进行扩展到复杂的内容上——两个库产生相同的行为

我们将两个库 L1 和 L2 定义为：如果它们在**每个调用程序**中都产生相同的输出概率，则称这两个库“具有相同的行为”

> 可互相交换库

1. 存在两个库 L1 L2 具有相同接口：具有相同名字的子程序和相同类型的输入参数和输出参数
2. 我们使用 `L1≡L2` 说明这两个库具有可互相交换：任意调用程序访问这两个库中的任何一个，两个库的展示的行为都是相同的
3. 如果我们使用概率说明 `Pr[A⋄L1⇒true]=Pr[A⋄L2⇒true]`

那么这里我们就可以考虑一个让调用程序作为一个区分者 目的是在连接到L1 L2的时候基于行为分辨出哪个是哪个

如果没有任何区分器能够成功，即使输出概率发生最小的变化，这两个库就是可互相交换库

这里我们还需要规范一下调用程序能做到和不能做到的内容：

1. 调用程序没有权限访问库中变量
2. 调用程序无法测量库中子程序执行时间，或者基于缓存区分析执行代码和取得变量

在上面 `Pr[A⋄L1⇒true]=Pr[A⋄L2⇒true]` 注意 我们关注的是 两个独立程序执行

而不是把L1和L2 一起分析

让我们回到 OTP的例子 基于上面 我们可以得到两个可互相交换库

![image-20261020150105728](https://raw.githubusercontent.com/Xioaruan912/pic/main/20261020150105759.png)

也就是说 没有敌手可以区分 到底是通过 OTP产生的还是通过 均匀选择产生的——基于子程序的输出无法区分

我们这里对敌手A没有任何的显示，但是对于两个库要求 即使运行时间完全不同，输出的概率也必须相同

## 如何构建interchangeable

上面说了两个库是 interchangeable 但是如何构建？

- 在代码中 它们唯一的区别在于无法执行的代码行
- 在数据中 它们唯一的区别在于它们给一个从未实际使用的变量赋予的值
- 在循环中 它们唯一的区别在于，一个库会展开另一个库中发生的循环
- 在函数调用中 它们唯一的区别在于，一个库内联了另一个库中发生的子程序调用

其实我们记录这些没意义，因为我们只要关注，对于任何的调用程序，两个库会不会产生相同的概率，让调用程序无法区分即可

# 2.3. How to distinguish two libraries

那么这里我们如果需要证明一个方案是不安全 我们需要如何说明？

其实就是说明 这个方案在两个原本可以互相交换的库中，基于敌手的操作，展现出来是不同的成功概率，这样证明出其实这两个库是不可互相交换的，从而证明敌手攻击成功

![image-20261020160507058](https://raw.githubusercontent.com/Xioaruan912/pic/main/20261020160507123.png)

这里是具体的步骤

1. 确定哪两个库被包含在里面
2. 编写调用程序，这个程序的目的是让这两个库展现出不同的成功概率
3. 计算这两个概率的差值，如果不同，攻击就成功

# 2.5. Abstract cryptographic primitives

这里我们会进入一些专业名词，正如标题说的 `原语`

我们会把 加密方案 抽象 成密码原语，后续内容我们只需要定义在原语上即可

- 语法：定义了基础接口，输入/输出类型，长度和使用什么算法
- 正确性：密码原语是否具有正确的，是否可以正常解密
- 安全属性：保证基于某个攻击场景下，密码原语能够安全

## SEK密码原语

下面我们会使用一个 对称加密算法 来说明原语

> 一个 SEK（对称加密算法）由下面算法组成，这里可以叫做 SEK原语

- Enc: 是一个概率算法，输入k in K 明文m in M 输出密文 c in C
- Dec：是一个确定算法，输入k in K 密文 c in C 输出明文m in M

其中 K是密钥空间 M是明文空间 C是密文空间

我们还可以使用符号 `Σ` 来表示整个密码原语

`Σ.Enc` 表示加密 `Σ.Dec` 表示解密 等等

在这里我们就已经了解到了什么是密码原语，下面我们会进入 他的三个基本属性

# 2.6. Modular cryptographic constructions

密码构建的模块化

密码原语和搭积木一样，我们可以使用模块化构建出更加 复杂的内容

也可以基于密码原语的安全假设，构建出更安全的组件

这里我们会给出一个模块化例子

> Alice和Bob通信，约定好发送M给Bob 并且商定了密钥K，Alice会做下面的事情

1. 重新采样一个新的K‘
2. 使用K 加密 K’ 得到 C1
3. 使用 K‘ 加密M 得到 C2
4. 发送(C1,C2) 给Bob

Bob只要做相反的事情即可

1. 使用K解密C1 得到K’
2. 使用K’解密C2 得到M

可以发现 这里构建的`全新`密码方案 其实就是两个已经存在并且简单的方案构建而成的——这里就是使用了模块化

这里可以发现 我们并没有说 Alice如何加密 Bob如何解密的，所以 这里理论上可以填写进入任何的加密方案

# 2.7. ☆ “Real-or-random” vs. “left-or-right”

安全属性要实现的方法其实不只有一种

在本书上 我们定义安全一般使用的是Real-or-random

## Real-or-random

内容是安全的，只要你的输出看起来是随机均匀分布的

这里其实就是OTP之前的想法，输出看起来都是1/2^n分布中随机抽取的，那么你算法就是安全的 

但是这个方法其实不是唯一的方法

## left-or-right

一个加密方案是安全的，如果你一个明文加密后看起来和其他明文差不多——但是不一定要满足均匀分布

在这个方案中，敌手要做的就是选择两个明文，送入加密，得到一个密文，需要猜测到底是 哪个自己选择的明文加密得到的

可以发现 这里改变的就是有 M的不同输出

## 两个定理的关系

满足 Real-or-random 的密码方案也会满足Left-or-right ，反之不是

![image-20261021101404882](https://raw.githubusercontent.com/Xioaruan912/pic/main/20261021101404915.png)

要说有没有特例？ 其实有 但是实际应用中 这个满足与否的差距非常小，我们会在后面内容中看到有一个算法，它在左右意义上安全，但在真实性或随机性意义上不安全

我们到底选择哪个其实没有正确与否之分，需要基于密码方案具体分析

- Left-or-right 在很多实际加密应用中看作是更加标准的方法
- Real-or-random 在很多非加密原语中看作是标准方法
- Real-or-random 在本书中更加方便和简单
- Real-or-random 的安全证明 长度一般是 Left-or-right  的一半
- Left-or-right  更符合 对安全产生的许多自然直觉。
